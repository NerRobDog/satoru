# Режимы запуска: дизайн

Статус: реализовано в ветке `launch-modes` (satoru) и `unified-launcher` (пак PW).
Первый потребитель — Prime World: один «Prime World.app», по двойному клику — выбор
«Оффлайн против ботов / Подключиться к серверу / Создать сервер и играть», прошлый
выбор подсвечен, ник и сервер спрашиваются при первом разе и запоминаются. В TUI — те
же пункты в меню игры.

## Как пак объявляет режимы

Опциональное расширение contract 1. Пак без `[modes]` работает байт в байт как раньше
(тот же шим, тот же TUI).

```toml
[modes]                              # порядок строк = порядок в списке
offline = "Оффлайн против ботов"     # id = метка
client  = "Подключиться к серверу"
host    = "Создать сервер и играть"

[setting_nick]                       # одна секция на параметр: setting_<имя>
label   = "Ник"
modes   = ["client", "host"]         # каким режимам нужен
pattern = "[A-Za-z0-9_-]{1,16}"      # POSIX ERE, целиком, без \ и [:class:]
error   = "Ник: латиница, цифры, _ или -, до 16 символов"

[setting_server]
label = "IPv4-адрес сервера"
kind  = "ipv4"                       # text (по умолчанию) | ipv4
modes = ["client"]
```

`[commands] launch` остаётся одной командой. Отдельных `launch_<mode>` нет.

## Как выбор доходит до пака

Только через окружение команды `launch`/`launch_plain`:

```
SATORU_MODE=client
SATORU_SETTING_NICK=Player_1
SATORU_SETTING_SERVER=192.168.0.116
```

Экспортируются только параметры выбранного режима. Пак без `[modes]` этих переменных
никогда не видит.

## Где живёт окно выбора

В шиме (`SATORU_GAME_HOME/launch`), а не в `Contents/MacOS/launch` бандла. Бандл
(ветка `satoru-try-dev`) делает `exec home/launch "$@"` и не меняется.

Шим, у пака которого есть режимы:

1. `SATORU_MODE` уже задан (TUI, скрипт) — диалога нет; значения берутся из
   `SATORU_SETTING_*`, недостающие — из сохранённых.
2. Иначе — `osascript`: `choose from list` (подсвечен прошлый режим; последний пункт —
   «Change settings…»), затем `display dialog … default answer` для каждого параметра
   режима, которого ещё нет или который перестал проходить проверку. Неверное значение —
   `display alert` с текстом `error` и повторный вопрос с тем же значением.
3. Отмена в любом окне — exit 20 («человек сказал нет»), ничего не сохраняется, игра не
   стартует. Не удалось показать окно (нет GUI-сессии) — exit 10 с подсказкой задать
   `SATORU_MODE`.
4. Выбор сохраняется, экспортируется, команда пака запускается. Если терминала нет
   (двойной клик), stderr пака собирается и при ненулевом коде показывается
   `display alert` — иначе отказ пака (exit 2/10) уходит в никуда.

## Хранение

`SATORU_GAME_HOME/satoru-launch.conf`, пишет satoru (шим или TUI), атомарно:

```
mode = client
setting_nick = Player_1
setting_server = 192.168.0.116
```

`key = value`, одна строка, читается `case`/split, никогда не `source`.

## Валидация

Двухслойная. satoru проверяет в цикле ввода (Python — `re.fullmatch`, шим —
`grep -Eqx`; IPv4 — одна и та же функция по смыслу в обоих) и переспрашивает. Пак
проверяет ещё раз и отказывает по контракту (exit 10 или свой код), потому что его
можно запустить и без satoru. `--check` проверяет объявление: id режимов, уникальность
меток, ссылки `modes` на существующие режимы, `kind`, компилируемость `pattern`.

## Решения

1. **Метки и порядок — `[modes] id = "метка"`.** Читатель сохраняет порядок ключей,
   значит одна таблица даёт и список, и подписи без массивов таблиц, которых в
   подмножестве нет.
2. **Параметр — своя секция `setting_<имя>`, ссылается на режимы (`modes = [...]`).**
   Вложенных таблиц нет; однослойный заголовок с `_` легален. Параметр, общий для двух
   режимов (ник), объявляется один раз и спрашивается один раз.
3. **Env, не аргументы и не `launch_<mode>`.** Аргументы уже заняты (`--plain`, свои
   флаги паков) и позиционно хрупки; отдельные команды на режим размножили бы
   `launch_plain` на каждый режим. Env сочетается с `--plain` бесплатно.
4. **Окно — в шиме.** Режимы приходят из манифеста пака и меняются с его обновлением;
   шим переписывается при каждом install, бандл — нет (Spotlight/Dock не трогаются).
   Одна логика на .app и на ручной запуск `home/launch`; TUI задаёт `SATORU_MODE` и
   окно не вызывает.
5. **Только `osascript` (AppleScript), без сторонних библиотек и без python.** На
   чистом macOS python3 может не быть; `choose from list`/`display dialog`/
   `display alert` есть всегда. Пользовательский текст передаётся через `argv`
   (`on run argv`), а не склейкой в литерал — экранировать нечего.
6. **Состояние — в доме игры, рядом с шимом.** Удаляется вместе с игрой, переживает
   переустановку (install дом не стирает), шим находит его без путей из конфигурации.
   `installed.toml` не трогается: там только факт установки.
7. **Спрашивать при первом разе; менять — пунктом «Change settings…».** Каждый раз
   переспрашивать ник — лишние клики; без пункта смены неверный IP нельзя исправить из
   .app. Невалидное сохранённое значение (правило поменялось в обновлении пака)
   спрашивается заново.
8. **Отмена — exit 20.** Код контракта «человек сказал нет»; TUI и бандл не считают это
   поломкой.
9. **Строки самого окна (заголовок-вопрос, «Change settings…», кнопки) — английские**,
   как весь интерфейс satoru; метки режимов и параметров — на языке пака. Локализация —
   отдельная задача.
10. **PW: env побеждает `lan.conf`, `lan.conf` не пишется.** Под satoru единственный
    источник — `satoru-launch.conf`; без satoru `lan.conf` работает как раньше. Писать
    одно в другое — два хранилища, которые разойдутся.

## Совместимость

- Пак без `[modes]` — без изменений.
- Пак с `[modes]` на satoru без этой ветки получит `unknown section [modes]` в
  `--check`. Значит порядок: сначала релиз satoru с режимами, затем манифест пака с
  режимами в каталоге (тот же порядок «паки → зонтик», каталог живёт в зонтике).
- Генератор бандла (`write_bundle`) пока в `satoru-try-dev`; при слиянии обеих веток
  конфликтов в шиме нет — бандл зовёт шим.
